OSP-Lite — The Edge Profile

The Omni-Swarm Protocol constrained to sub-1.5B models on phones, running as a service — designed for harnessdroid (Android service host) and WhatsApp (chat-app transport). Companion to the full profile (v0.4).

0. Why a Second Profile

The full protocol (v0.4) assumes the model can afford multi-sample gates, verbalized confidence passes, and full-payload resolution. On a mid-range phone running a 0.5–1.5B model at 4-bit, one generation is 5–12 seconds — the expensive resource is not bandwidth, it is model invocations. OSP-Lite is not a reduced OSP; it is the same protocol with its cost structure inverted: generation-once, decide-cheap-always.

Full profile (v0.4) Lite profile (v0.5)
Target model 3B–8B quantized 0.5B–1.5B, 4-bit (Q4_K_M), ~0.4–0.9 GB resident
SLM generations / query ~6 (k-sample gate, verbalized pass, mapping, answer) 1 (only the auction winner generates)

1. The Decision Ladder — the core optimization

Most protocol decisions do not need a language model at all. OSP-Lite classifies every decision onto a four-rung ladder and enforces one rule: a decision MUST use the lowest rung that suffices.

Rung Mechanism Cost (mid-range phone) OSP decisions
D0 Vector math: Hamming (popcount) / cosine over binary-quantized embeddings ~µs, no model loaded Routing, centroid match, quorum aggregation, similarity scoring
D1 Linear probes: SEP head [R2] over embedder hidden states, calibration tables ~0.1 ms Bid gating (hallucination-risk pre-screen), conformal lookup
D2 Small cross-encoder NLI (e.g. DeBERTa-v3-xsmall class, ~70M, int8) ~10–30 ms / pair Chunk-agreement gate, payload entailment (VERIFY), audit
D3 The SLM itself (0.5–1.5B, 4-bit) 5–12 s / 200 tokens Only: ontology mapping on cache miss, and answer generation for the winning bid
1-bit packing: 384d float32 = 1536 B → int8 = 384 B → binary = 48 B (+ fp32 scale) 1M chunks ≈ 48 MB of vectors + text. Query side stays float (asymmetric scoring [A8]). Generation budget rule: budget(SLM, node) = N_gen/day (default 50, configurable) D3 calls MUST be charged to the budget; exhausted budget → node bids D0/D1 scores only and abstains from RESOLVE.

2. The Lifecycle, Reground for Cheap Decisions

Same five steps, restructured so that generation happens exactly once.

01

PROPOSE (D0 — no model)

Origin quantizes the query to a 384-bit code, matches it against its cached centroid codebook (48 B per centroid per peer), and submits the query to its chosen channel. In hub mode that is one WhatsApp group — star topology, loop-free by construction, no trail needed beyond provenance. In mesh mode it is the full path-vector forwarding of the base protocol.

02

PRE-BID (D0+D1+D2 — zero generation)

Each responder retrieves top chunks and scores a generation-free bid: retrieval similarity (D0), cross-chunk agreement — pairwise NLI over the top-3 chunks (D2), the SEP probe on hidden states (D1), and reputation. Honest substitution: full semantic entropy [R1] needs sampled generations, so Lite uses retrieval-side agreement as its proxy; the full gate remains available in mesh mode with bigger models. A conformal coverage number comes from the node's calibration table [R3] — a lookup, not a computation. The SLM is not loaded.

03

ALIGN (cache-first, C = 1)

Mapping is LRU-cached per (peer, concept-pair) with a 7-day TTL and validated evidence [R9][R10]; D3 runs only on a cache miss. At most one clarify round is permitted (C = 1); the contraction rule of the base protocol (dn+1 ≤ γ·dn) still applies — no progress still aborts with MISMATCH.

04

RESOLVE (the single generation)

Only the auction winner loads the SLM. It generates a ≤ 128-token answer over its retrieved chunks and ships digest-first: chunk hashes + a 256-character head (≤ 2 KB). The origin pulls the full chunk only if VERIFY flags ambiguity — saving ~70 % of payload bytes on chat transports.

05

VERIFY (D2, reputation-scaled audit)

The origin runs entailment on the answer against the digest (and full chunk if pulled). Audit intensity scales with reputation: unknown nodes are verified 100 %, warm nodes 25 %, trusted nodes every 8th query with mandatory spot audits. Over-bidding is caught by a sequential probability ratio test over realized groundedness — the conformal promise each node makes in its bids is audited statistically, not per-message.

3. Wire Format — CBOR-Lite

Deterministic CBOR [A1] with a COSE Ed25519 signature [A2] replaces verbose JSON. The signature covers the canonical CBOR bytes, so text transports that normalize Unicode or trim whitespace can never invalidate a packet — they only touch the base64url wrapper.

4. Transport Bindings

Hub mode — WhatsApp

The group chat is the overlay

A WhatsApp group is a topic-scoped channel: its description carries the topic centroid (48 B). One PROPOSE reaches every member in one message — routing collapses to channel selection (D0), loops are topologically impossible, and the path-vector machinery is only needed for the mesh fallback.

  • Message anatomy: two human-readable lines (so group members can judge or mute the traffic) + OSP1: + base64url blob. ASCII-only — safe against client text mangling.
  • Chat-speed timers: bid window Tw = 10 min (vs 5 s in mesh). NO_QUORUM retries back off exponentially (30 min → 2 h → next day), bounded by R = 2.
  • Rate discipline: WhatsApp enforces per-number messaging tiers and throttles [A6] — centroid advertisements are batched to ≤ 1 message/day/group, queries are coalesced, and the service treats WhatsApp as store-and-forward with no delivery guarantee: jti dedup + origin-side ACK provide the actual reliability.
  • Metadata honesty: WhatsApp gives transport-level encryption, not OSP-level authenticity — Ed25519 signatures stay the source of truth. Meta observes traffic metadata; topics considered sensitive SHOULD enable the optional payload encryption (X25519 + AEAD, keys via the node key directory) and SHOULD assume topic names leak.
Mesh mode — direct

When devices can see each other

On LAN or Bluetooth, harnessdroid nodes connect directly (TCP or BLE) and run the full profile rules: path-vector trails, G = 4, Tw = 5 s, full semantic-entropy gates. Hub and mesh interoperate — a query that finds no quorum in its WhatsApp channel may be re-proposed on mesh to co-located nodes before threshold decay.

5. The harnessdroid Service

Assumption stated: ../harnessdroid does not exist yet on disk; this section specifies the service contract an Android host must satisfy.

app(s) ──AIDL──▶ OSP-Lite Service (foreground, type=dataSync) ├─ Router D0 · centroid cache (48 B/centroid, LRU) ├─ Gatekeeper D1 SEP head · D2 NLI (ONNX int8) ├─ Negotiator mapping LRU · conformal tables · stakes tiers ├─ Verifier D2 · audit scheduler (reputation-scaled, SPRT) ├─ Transport WhatsApp bridge (NotificationListener/Cloud API) │ · mesh (TCP/BLE, RFCOMM) └─ Store SQLite + packed 48 B bitvectors ▲ shared runtimes, one instance each llama.cpp (SLM 0.5–1.5B Q4) · ONNX Runtime Mobile (embedder 384d) // IOspService.aidl interface IOspService { String submitQuery(in String text, in int stakesTier); // → queryId void registerCallback(in String queryId, in IOspCallback cb); void advertiseCentroid(in byte[] cborCodebook); // ≤ 1 KB byte[] fetchKeyBundle(in String nodeId); // Ed25519 + X25519 prekey } oneway interface IOspCallback { void onOutcome(in String queryId, in int mode, in String answer, in byte[] verifyReport); }
  • Runtimes: llama.cpp or MediaPipe LLM Inference [A4][A5] for the SLM; ONNX Runtime Mobile for the embedder, NLI cross-encoder, and SEP head. One shared model instance; requests are coalesced across apps.
  • Scheduling: gossip, centroid advertisement, and calibration refresh run as WorkManager jobs constrained to unmetered + charging [A7]; foreground queries are exempt. Doze-safe: no always-on sockets in hub mode.
  • Budgets: SLM ≤ 50 generations/day (configurable); ≤ 4 background wakeups/day; RAG store of 1M chunks ≈ 48 MB vectors + SQLite text.
  • Battery rule: when the generation budget or battery saver is active, the node degrades to D0/D1-only participation — routing and pre-bidding stay alive, generation stops.

6. Convergence under Lite Constraints

The four structural rules of the base protocol survive untouched, and the bounds actually tighten:

  • Gas G = 3, C = 1, R = 2 → worst case 6 rounds instead of 10.
  • Hub mode is loop-free by construction (star topology); C2's trail check remains as provenance and for mesh mode.
  • T1 quorum (k=2, q=2, distinct chunk hashes) needs both votes to agree on independent evidence — error p² = 1 % at p = 10 %, better than the full profile's 2.8 %, at the cost of needing a second responder (else the query falls back to T0: single answer, 100 % verified).
  • Honest caveat: reputation-scaled audit (1-in-8 for trusted nodes) trades the per-message guarantee for a statistical one — the SPRT bounds the expected number of unverified bad answers accepted per interval; a single audit failure resets the node to 100 % verification. This is a deliberate economy, not an omission.

8. Known Limits

  • Verbalized confidence is dropped [R4]. Its evidence base is RLHF-scale models; on 0.5B models it is unreliable, so Lite bets on retrieval similarity + SEP + reputation. If the SLM grows, the field returns.
  • The semantic-entropy gate is a proxy here. Cross-chunk NLI agreement approximates, but does not equal, sampled semantic entropy [R1]; it can miss a model that confabulates consistently with its retrieved chunks.
  • Audit sampling weakens per-message guarantees to statistical bounds (see §6) — deliberately, for energy.
  • WhatsApp is a third-party dependency: rate tiers [A6], metadata exposure, account bans, and no delivery SLA. The mesh binding exists precisely so the protocol survives WhatsApp's absence.
  • The CBOR blob is opaque to humans — the two-line preamble is the only human-auditable part of a message.
  • All §7 numbers are modeled, not measured. First implementation milestone is a hardware benchmark, not a feature.
